# Player docs vault

`player-docs/` is an Obsidian vault of player-facing documentation, separate from `decisions/`, `specs/`, `docs/knowledge/` and code. Notes in it carry no `dte:` citations and no implementation detail: this spec is how the vault cites what it serves.

Every project players can get has a **folder** in `player-docs/Projects/` named after it (owner, 2026-11-14): an **overview page** with the project's name (started from the matching template in `player-docs/Templates/`, with frontmatter `type`, `minecraft`, `status` (`active` or `paused`) and `modrinth`) that links every page in the folder, plus **one page per topic** (a feature, a mechanic, commands and settings). Page names are unique across the whole vault so `[[links]]` resolve; topic pages start with the hatnote `*Part of [[<project>]].*` Internal projects (`refmod`, `refpack`) get no pages.

A change that alters what players see (a feature, a command, a keybind, a config option, a dependency, the supported Minecraft version) ends up on the project's pages: builders note it in `docs/reports/`, and the orchestrator or a docs agent merges it.

**Docs reports (owner: builders build; docs are merged separately).** A builder agent doesn't edit `player-docs/` or spec prose. It writes what the docs need (player-facing changes, spec facts, numbers, owner decisions, its own choices marked as such, questions for the owner) into `docs/reports/<project>-docs-<date>.md` and commits it. The orchestrator or a docs agent merges reports into `specs/` and `player-docs/`, checking numbers against the code (the code wins), then deletes each merged report. Builders still write API contracts other builders need, `covers:` lines and generated data or reports themselves.

`Version Status.md` names the current Minecraft version and lists every project that is paused on it, with a plain reason (B10 alwaysLatest).

Pages use plain language: what it does, how to use it, what it works with. Specs say how things are built; the vault says how to use them. Images in the vault are made by people, never generated by AI.

`Home.md` links every project's overview page and the getting-started guides (including the test world page).

## Style (owner, 2026-11-14: mimic minecraft.wiki)

Pages read like minecraft.wiki articles, written for plain Obsidian (no plugins, no CSS snippets).

- **Lead:** the first sentence names the subject in bold and says what it is: "A **sleeping undead** is a dormant skeleton or zombie that...". The project name opens the overview page the same way ("**Bubba's Reworked Mobs** is a Fabric mod that..."). One short lead paragraph, then sections.
- **Voice:** encyclopedic, third person, present tense, neutral: "the player", not "you"; no jokes or exclamation marks. Mod-only behavior is stated as plain fact about the mod, not as an edition note. Early-version caveats ("placeholder art", "not yet") are stated once, plainly.
- **Hatnotes** (italic lines under the title or a heading): every topic page opens with `*Part of [[<project>]].*`; a section summarizing a topic that has its own page opens with `*Main article: [[Page]]*`; `*See also: [[Page]]*` for related pages.
- **Infobox:** right after the hatnote, a callout `> [!infobox] <Name>` holding a two-column table of key facts (type, version, requirements, stats, how obtained, renewable, stackable...). Only facts the page backs up; no images. Overview pages and topic pages about a thing (item, block, mob) get one; mechanics pages get one only if they have a few clean facts; tutorial pages never.
- **Section order** (use only those with content): Obtaining (or Spawning / Generation), Usage (or Behavior), mechanics subsections, Crafting/Smelting tables, Commands, Compatibility, Textures, Installation, History, Trivia, See also. Never invent sounds, gallery images, history entries or trivia.
- **Tables** for recipes (columns: Name, Ingredients, Result or Pattern, Time, Experience), stats and comparisons. Crafting-table shapes are written as a 3x3 grid table inside the recipe's section.
- **History:** a short table or list by project version ("0.1.0: Added."), drawn only from what shipped; development-only changes are left out.
- **Tutorials:** `Getting Started/` pages are written like minecraft.wiki "Tutorial:" pages: a one-sentence purpose ("This tutorial explains how to..."), numbered steps in the imperative, short notes; no infobox.
- **Home** reads like the wiki's main page: a welcome line, then lists of projects and tutorials.
