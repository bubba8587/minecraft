# Player docs vault

`player-docs/` is an Obsidian vault of player-facing documentation, kept apart from `decisions/`, `specs/`, `docs/knowledge/` and the code. Its pages carry no `dte:` citations and no implementation detail; this spec is how the vault is tied to the tree.

## What goes in the vault

- **One folder per project** players can get, in `player-docs/Projects/`, named after the project (owner):
  - an **overview page** with the project's name, started from the matching template in `player-docs/Templates/`, with frontmatter `type`, `minecraft`, `status` (`active` or `paused`) and `modrinth`. It links every page in the folder.
  - **one page per topic**: a feature, a mechanic, commands and settings. Topic pages start with the hatnote `*Part of [[<project>]].*`
- Page names are unique across the whole vault, so `[[links]]` resolve.
- Internal projects (`refmod`, `refpack`) get no pages.
- **Only what is in the game on `develop` now.** Designed or in-progress features stay in `specs/` and `specs/STATUS.md` until they are merged. A project still on its own branch gets no page.
- **Every change players would notice** (a feature, command, keybind, config option, dependency, or the supported Minecraft version) ends up on the project's pages.
- `Version Status.md` names the current Minecraft version and lists every project paused on it, with a plain reason (B10 alwaysLatest).
- `Home.md` links every project's overview page and the getting-started guides, including the test world page.
- **Plain language:** what it does, how to use it, what it works with. Specs say how things are built; the vault says how to use them.
- **Current state only (owner):** pages describe how things are in the game today. No History sections, version or changelog tables, dated notes, or wording that describes a change ("was X, now Y", "used to", "no longer", "previously", "(new)", "now" meaning "since a change"), and no mentions of earlier versions or old behaviour. When something changes, the page is rewritten to the new state.
- **Bullet points (owner):** after the lead sentence, content is concise bullet points (what it is, how to get it, how it works); tables where they are clearer (recipes, stats, chances). No paragraphs of prose.
- **Images are made by people**, never generated by AI.

## Docs reports (owner: builders build; docs are merged separately)

- A builder agent doesn't edit `player-docs/` or spec prose.
- It writes what the docs need into `docs/reports/<project>-docs-<date>.md` and commits it: player-facing changes, spec facts, numbers, owner decisions, its own choices (marked as such) and questions for the owner.
- The orchestrator or a docs agent merges reports into `specs/` and `player-docs/`, checks the numbers against the code (the code wins), then deletes each merged report.
- Builders still write these themselves: API contracts other builders need, `covers:` lines, and generated data or reports.

## Style (owner: mimic minecraft.wiki)

Pages read like minecraft.wiki articles, written for plain Obsidian (no plugins, no CSS snippets).

- **Lead:** the first sentence names the subject in bold and says what it is: "A **sleeping undead** is a dormant skeleton or zombie that...". The overview page opens the same way with the project name ("**Bubba's Reworked Mobs** is a Fabric mod that..."). One short lead sentence, then sections of bullet points.
- **Voice:** encyclopedic, third person, present tense, neutral. "The player", not "you"; no jokes or exclamation marks.
  - Mod-only behavior is stated as plain fact about the mod, not as an edition note.
  - Early-version caveats ("placeholder art", "not yet") are stated once, plainly.
- **Hatnotes** (italic lines under the title or a heading):
  - every topic page opens with `*Part of [[<project>]].*`;
  - a section summarizing a topic that has its own page opens with `*Main article: [[Page]]*`;
  - `*See also: [[Page]]*` for related pages.
- **Infobox:** right after the hatnote, a callout `> [!infobox] <Name>` holding a two-column table of key facts (type, version, requirements, stats, how obtained, renewable, stackable...).
  - Only facts the page backs up; no images.
  - Overview pages and pages about a thing (item, block, mob) get one; mechanics pages only if they have a few clean facts; tutorial pages never.
- **Section order** (use only those with content): Obtaining (or Spawning / Generation), Usage (or Behavior), mechanics subsections, Crafting/Smelting tables, Commands, Compatibility, Textures, Installation, Trivia, See also. Never invent sounds, gallery images or trivia. No History section.
- **Tables** for recipes (columns: Name, Ingredients, Result or Pattern, Time, Experience), stats and comparisons. A crafting-table shape is a 3x3 grid table inside the recipe's section.
- **Tutorials:** `Getting Started/` pages are written like minecraft.wiki "Tutorial:" pages: a one-sentence purpose ("This tutorial explains how to..."), numbered steps in the imperative, short bullet notes, no infobox.
- **Home** reads like the wiki's main page: a welcome line, then lists of projects and tutorials.
